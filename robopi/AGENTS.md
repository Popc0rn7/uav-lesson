# RoboPi 开发与交付约定

本目录维护实际要传到 OpenHarmony RoboPi 的课程程序、启动脚本及配置。PC 部署工具留在 `stageN/`，双 Docker 仿真留在 `develop/` 和各阶段目录。RoboPi 替代 ROS 算力容器，PX4/Gazebo、QGC、可视化及真值评测继续在 PC；算力算法不部署到 PX4。

## 文件与部署边界

- `stage1/` 对应板端 `/data/local/workspace/stage1/`；PC 部署入口为 `python3 stage1/deploy.py --target <connect-key>`，设备标识不写入源码。迁移只改变 PC 源路径，板端路径保持原值。
- `stage1/qwen_infer/` 是忽略 Git 的上游运行产物，获取及部署步骤只维护在 [教师准备流程](../docs/AGENTS.md)。不要维护其 C++、转换工程或构建源码副本。
- 模型缓存留在 `artifacts/models/`，按部署入口传到板端 models 目录；不在本目录复制大模型。
- `stage3/` 维护 AirSim/SUPER 板端启动、进程管理、DDS 与共享源码链接；PC 打包时解引用链接，单独加入目标构建 install。入口与未验证边界见 [AirSim README](../stage3/super/airsim/README.md#robopi-算力后端2026-10-16迁移验证中)。
- 新阶段只有出现实际板端文件才建立目录。Stage 5 尚无板端交付物；不复制 PC 目录制造迁移完成的假象。
- 不整体发送本目录或仓库。按部署入口选择交付文件，排除 AGENTS.md、skills、测试、缓存、日志和凭据。现有 Stage 1 使用显式文件清单。

板端手工修复需要同步回本目录或所属上游，再经相同部署流程验证；不要让设备成为唯一源码。共享算法维持单一源码位置，板端目录只维护需要的适配和交付配置；目标构建产物忽略 Git，记录其来源、SDK、源码提交和依赖。

## 双 Docker 到 RoboPi 的迁移流程

1. 固定 PC 基线：记录原 image 摘要、派生 Dockerfile 及其增量、实际挂载清单、启动命令、源码、场景与任务。按“原 image → Dockerfile 增量 → 挂载内容”的顺序逐层对齐；每层记录输入、板端对应物、留在 PC 的例外及通过证据，避免每次重新摸索整个环境。
2. 对齐原 image 的运行基线：检查板端已有 ROS、RMW、基础消息及运行库，核对 OpenHarmony/AArch64、libc、Python ABI 和 SDK。能力/接口对齐不要求复制 Linux 系统或重建已经核验的板端 ROS；换镜像才重新核验对应层。
3. 对齐 Dockerfile 增量：逐项映射新增运行依赖、固定源码版本、环境变量与入口。编译工具留在 PC，运行依赖按目标 ABI 提供；Agent、仿真桥等因系统分工留在 PC 的项目明确列出，不把整个 apt 清单盲目搬上板。
4. 对齐挂载内容：Python 与配置按单一源码打包，C++、自定义消息和 native 扩展交叉编译，部署解引用共享链接；保持输入配置和相对资源结构。记录构建选项和依赖闭包，Linux 容器的 install 不能直接作为板端产物。
5. 三层对齐后核对启动契约：source 顺序、路径、无人机标识/命名空间、ROS 域、DDS QoS、坐标系、单位、频率、仿真时间与墙钟看门狗。PC↔RoboPi 跨机 ROS 默认使用独立以太网 DDS、显式接口/单播 peer 与 PC 必需回环；操作只维护在 AirSim README 的“板端以太网通信”。HDC 管理和以太网运行通道分别检查，真值只用于 PC 评测。
6. 构建和部署逐项预检，检查 ELF、消息 ABI、完整运行依赖与文件校验；按显式设备发布独立可回退版本，不覆盖未知文件或停止无关服务。已核验且输入未变的层复用其产物/证据，变化时只重建和回归受影响部分。
7. 按“板端加载/import → 实际消息双向收发 → 静止传感器/状态 → 最小闭环 → 完整任务与故障处理”逐级验证；在本次任务授权范围内操作仿真，实机单独验收。
8. 与固定 Docker 基线比较并保留日志和 ULog。性能不足时先 profile 区分计算、等待和通信；只有显式授权的独立降级配置可调整相应门限，记录原因、适用速度、失败行为和实测结果，原基线保持可复验。更新 Validation 和唯一操作入口，降级通过不写作原基线通过。

## 当前验收边界与排障

截至 2026-10-16，Stage 1 新布局完整部署、真实以太网 ROS 文本、非法请求、桥重启常驻复用、并发拒绝和单图 VQA 已通过。Stage 3 单容器 PC 镜像与无显示 Docker 短程/forest1/forest10 基线已通过，跨机 DDS 已实测；完整目标构建、板端加载/消息序列化和板端短程及 forest1 往返已通过，低速四项故障降落通过；forest10 首轮失败，三次成功冷启动待完成。证据见 [迁移验证](../docs/stage3/RoboPi-validation.md)。Stage 5 迁移待实现。后续 profile 和首个拉长前视候选发生碰撞；保留原前视的双时钟预算候选已在连接恢复后部署，关闭 profile 的低速复验因 lidar cloud timeout 降落，候选未通过、未继续高速。后续 702 秒持续观测无应用队列丢弃，3939 帧全部完成配准，原始云空窗中捕获板端 IP 分片重组失败，传输问题尚未修复；暖重启任务另被旧规划指令偏差保护拒绝。本轮飞行实例已清理，Stage 1 保持 ready，HTTP 映射已恢复。5 m/s 的 200 ms 前视实验短时达到 5.194 m/s，但第 3/8 航点途中仍因点云失流降落，完整任务未通过。正式基线已改回 AB。AB 5 m/s 点云仅观察实验记录 6.598 秒空窗及继续前进 22.69 m，恢复后规划失败、停点保持到期，最终指令失流降落，无碰撞、未到 B；不能将自然失流后的所有规划失败直接归因于失流。编译、HTTP 健康或 DDS 收发不能代替板端飞行验收。

文件缺失先按教师准备流程检查上游 dist 和模型，不能用 Linux 产物补齐。连接失败先保存 HDC 错误并确认目标；HTTP 不通分别检查板端服务与本次端口转发；DDS 不通检查网卡、域、RMW、QoS 和时间。保留诊断，不通过重启整板、替换系统库或放宽控制约束掩盖问题。
